# SIMBAR 음원 스트리밍: 로컬 검증 및 운영 준비

이 코드는 로컬 검증용으로 준비된 제안이며, 운영 설정 변경이나 배포를 수행하지 않는다. 사용자가 사용권을 확인한 다섯 곡만 `track_001`부터 `track_005`까지 서버 측 목록에서 허용한다. 곡의 권리 상태가 바뀌면 서버 목록과 비공개 HLS 파일을 함께 관리해야 한다.

## 구조와 보안 범위

원본 MP3는 공개 접근이 없는 **별도의 비공개 원본 저장소**에 보관하고 Worker에 바인딩하지 않는다. Worker는 AAC로 변환한 HLS 인덱스와 조각만 보유한 **별도의 비공개 HLS 저장소**를 `STREAM_BUCKET`이라는 R2 바인딩으로 읽는다. 인덱스와 조각 경로는 서버가 검증해 생성하며 원본 MP3, 임의 객체, 목록에 없는 곡은 반환하지 않는다. 비밀 키나 원본 경로는 클라이언트에 들어가지 않는다.

공개 데모는 익명 방문자의 재생을 허용하므로 HLS 엔드포인트도 공개된다. 방문자는 조각을 가져오거나 녹음·재구성할 수 있다. 이 방식은 원본 파일의 공개 직링크를 차단하지만 DRM이나 무단 복제의 완전한 방지는 아니다. CORS는 브라우저 호환을 위한 설정이며 접근 권한 검증 수단이 아니다. 사용량·남용 방지 정책은 운영자가 별도로 정한다.

## 로컬 준비

1. 사용권이 확인된 원본 다섯 곡을 로컬 비공개 디렉터리에 `track_001.mp3`부터 `track_005.mp3`까지 준비한다. 디렉터리와 파일은 Git에 추가하지 않는다. 테스트 과정에서 확보한 원본은 무시된 `Temp`에만 존재한다.
2. `uv run --with imageio-ffmpeg==0.8.1 python Tools/AudioStream/prepare-local.py --source-dir <비공개_원본_디렉터리> --output-dir <Git이_무시하는_새_임시_디렉터리>`를 실행한다. 서버용 `index.json`과 AAC MPEG-TS 조각은 지정한 디렉터리의 `store` 아래에 생성된다. 기존 재생 중인 저장소와 파일이 섞이지 않도록 매번 새로운 디렉터리를 사용한다. 변환기는 다운로드하거나 업로드하지 않는다. 검증 환경은 Windows, `imageio-ffmpeg 0.8.1`과 동봉된 FFmpeg `9.0.2-essentials`다. 재인코딩 손실을 줄이기 위해 192 kbps AAC를 사용하며, 변환 전 손실 압축된 원본과 완전히 같은 음질을 보장하지 않는다. 저장량과 전송량은 128 kbps보다 커진다.
3. `node Tools/AudioStream/local-server.mjs --store <임시_디렉터리>/store --port 8788`을 실행한다. 로컬 서버는 `127.0.0.1`에만 바인딩하고 원본을 제공하지 않는다. `node --test Tools/AudioStream/worker.test.mjs`로 라우팅·범위 요청·실패 처리 검사를 실행한다.

서버 계약은 `GET/HEAD /v1/audio/track_001/index.m3u8` 및 manifest에 들어 있는 상대 경로 `segment-00000.ts` 등의 HLS 조각이다. 다섯 곡의 ID만 허용하고 GET, HEAD, OPTIONS 및 단일 Range를 지원한다. 실제 게임의 플레이 카운트 로직은 이 서비스에 포함하지 않는다. 응답은 `no-store`이고 HLS manifest는 `application/vnd.apple.mpegurl`, 조각은 `video/mp2t`이다.

## 사용자 승인 후 운영에서 남은 작업

1. 원본의 안전한 백업과 권리 정보를 확인하고, 공개 기능이 없는 원본 전용 저장소와 **별도** HLS 전용 저장소를 준비한다. 다섯 곡의 HLS를 생성·검증해 HLS 저장소에만 올린다. `index.json`과 조각에 공개 접근이 켜지지 않도록 한다.
2. 기존 프로젝트에 Wrangler 설정이 없으므로 Cloudflare CLI 문서에 맞는 별도 Worker 프로젝트 설정을 준비하고 HLS 저장소만 `STREAM_BUCKET`에 바인딩한다. 기존 서비스와의 충돌, 사용자 정의 도메인, 관측 및 남용 방지를 검토한다. 준비된 Worker를 테스트 환경에서 먼저 검증한다. 설정 파일 생성이나 클라우드 변경은 이 로컬 작업에서 수행하지 않았다.
3. 웹과 새로운 Windows 빌드를 새 스트리밍 서비스에 연결해 공연·감상 모드, 다음 곡 자동 재생, 일시정지·이어듣기, 탐색과 재생 횟수 집계를 점검한다. Safari, Chromium 계열 및 Windows 실행 환경을 각각 확인한다. 이전에 배포된 웹·Windows 버전은 기존 공개 음원 설정에 의존하므로 차단 전에 업데이트와 안내가 필요하다.
4. 새 버전이 준비된 뒤 승인된 전환 시간에 기존 공개 R2 접근과 관련 사용자 정의 도메인 경로를 차단하고, 해당되는 CDN 캐시를 무효화한다. 기존 주소에 대한 외부 GET/HEAD가 더 이상 원본을 제공하지 않는지 독립적으로 확인한다. 이미 다른 곳에 저장된 사본이나 제3자 캐시는 회수할 수 없다. 전환 전에는 기존 공개 주소가 계속 작동한다.
5. 장애 시 새 방식의 직전 정상 Worker와 새 클라이언트 버전으로 되돌린다. 이미 공개 접근을 차단한 뒤 기존 웹·Windows 버전으로 되돌리면 음원이 재생되지 않는다. 원본 재공개는 별도 승인 없이 복구 수단으로 사용하지 않는다.
